# Implementation Plan: kiro-provenance

## Overview

The plan builds the Recorder, the Reveal_Command, the MCP server and the Power of `design.md` in the order that Requirement 18 (criterion 8) and Decision 14 make binding. Group 1 repeats the hook captures outside the repository and commits scrubbed fixtures. Group 2 makes the timeout of the five existing test hooks effective (Requirement 19). Groups 3 and 4 scaffold `packages/provenance` and build the pure core, each module followed by its property. Group 5 builds the Recorder around the core (file system, git, lock, deadline, Fault_Log). Group 6 installs the Recorder in this repository by hand, so that every later task is recorded, and measures the `promptSubmit` time. Groups 7 to 10 build the viewer, the MCP server, the setup command and the Power. Group 11 holds the boundary tests and the documentation. Group 12 is the final checkpoint. The Engine, the web app, the Verifier, the export package and `crew/sentinel` are not changed, except the two test edits of task 2.1.

**The Open points of the earlier design were settled by the user on 2026-11-18** and are recorded in the "Resolved points" section of `design.md`. The plan follows the design as it stands. A later change to a resolved point is made in `design.md` and in the affected tasks first.

Task count: **69 tasks**, counted as leaf sub-tasks (numbered `N.M`), the five checkpoints (1.4, 4.17, 4.20, 6.5 and 12.1) included. The twelve group headings are not counted. The dependency graph lists the 64 non-checkpoint leaves plus the five checkpoints, each in a wave of its own. Seventeen properties exist, one per task, none optional: Property 13 in 4.2, Property 10 in 4.4, Property 7 in 4.6, Property 3 in 4.8, Property 8 in 4.10, Property 9 in 4.12, Property 15 in 4.16, Property 17 in 4.19, Property 1 in 5.8, Property 2 in 5.9, Property 4 in 5.10, Property 5 in 5.11, Property 14 in 5.12, Property 16 in 5.13, Property 11 in 7.2, Property 6 in 7.4 and Property 12 in 7.6.

**The capture of task 1.2 and the user's decisions of 2026-11-18 changed the plan** (design, Resolved point 13; requirements, Decision 20): a session entry persists with an empty stack and records `lastClosedBy`, `promptSeen` and `noPromptCounted`; an `agentStop` that follows the same session's own `postTask` logs nothing; sessions that fire `Stop` with no prompt event are logged as `no_prompt_events` and counted in the committed file `.kiro/provenance/sessions.json`; the `[HUM]` and `[AI>HUM]` words now say "while no agent window was open"; and the CLI has no spec-task windows. Task 1.2 itself is unchanged and nothing is marked complete by this change.

Conventions that apply to every task:

- Paths are repository-relative. Source modules stay at 300 lines or fewer and functions at 40 lines or fewer. No `any`, named exports only, no default exports, no classes, plain data types and discriminated unions. Errors are `Result` values; only `src/cli/main.ts` may throw or call `process.exit` (Req 1.6, 1.7). Imports inside `packages/provenance/src` use `.js` specifiers like the Engine.
- `src/core/` imports no `node:` module. File system, git, process and clock access live in `src/io/` and receive their dependencies as an injected `Deps` value. `process.env` is read in `src/io/env.ts` only (Req 1.5, 1.8).
- Tests live in `packages/provenance/test/`. Example tests belong to the task that builds the module; they are not separate tasks, except where a task says otherwise. No network, no snapshot test of the Engine, no mock of the Engine, no `try/catch` that hides an error, no test that only imports a module (Req 16.15, 16.16). Tests that need git build a temporary repository.
- Property rules (`tech.md`, Req 16.1): each property is one `fc.assert(fc.property(...))` in a file named `<module>.properties.test.ts`, preceded by `// Property N` (the design's number) and inside a `describe` whose title ends in `_Requirements: x.y_`. `numRuns` comes from `runs(process.env)` in `packages/provenance/test/support/fc.ts` (200 locally, 500 in CI or with `FC_NUM_RUNS=500`). A property must assert a relationship between input and output. On a failing property, record the shrunk counterexample as a named example test and fix the code; never weaken the property. Any property the build had to change is listed in `BUILD_LOG.md` with the reason (Req 16.17).
- Arbitraries live in `packages/provenance/src/testing/arbitraries.ts`, which re-exports `arb-text.ts`, `arb-edits.ts`, `arb-windows.ts`, `arb-dirs.ts` and `arb-ignore.ts`. Task 3.2 creates all five files (`arb-text.ts` complete, the other four as `export {};` with a comment). Tasks 4.5, 4.10, 4.12, 4.16 and 5.8 each fill in one of them (4.10, 4.12 and 5.8 fill different parts of `arb-dirs.ts` in different waves), and no two tasks in one wave touch the same file. Arbitraries cover text with surrogate pairs, carriage returns, a byte order mark, empty text and text with `[`, `]` and `\` (Req 16.14). The exception to `tech.md` (arbitraries in this package, not in `packages/engine`) is one line in `BUILD_LOG.md` (Decision 17).
- Existing files change only as the requirements allow: root `package.json` (the `reveal` script, task 7.8), root `tsconfig.json` (one reference), `vitest.config.ts` (one project named `provenance`), `scripts/build-power.mjs`, `.prettierignore`, and the five test hooks with the two tests of task 2.1. `scripts/commit-task.sh`, `pnpm-workspace.yaml`, `apps/web`, `packages/engine`, `packages/verifier`, `packages/export` (but for task 2.1), `crew/sentinel` (but for task 2.1) and `data` are not edited (Req 15).
- The Bundle `.kiro/provenance/provenance.mjs` of this repository is a copy of `powers/provenance/server/provenance.mjs`. A task that changes `packages/provenance/src` after task 6.3 ends with `node scripts/build-power.mjs --power provenance` and `node powers/provenance/server/provenance.mjs setup`, so that the installed copy matches the sources (Resolved point 6). The freshness tests of task 10.2 fail otherwise.
- `docs/KIRO_USAGE.md` and the steering files are edited only in task 11.3. `BUILD_LOG.md` gets exactly one new entry for this spec, dated `YYYY-MM-DD`: task 1.3 creates it with the capture results, task 2.2 adds the Requirement 19 line, task 6.4 adds the measured times, and task 11.4 completes it (Req 17.5).
- Commits: spec files are committed by the user with the prefix `spec(kiro-provenance):` before task 1.1 starts (Req 18.1). The only commits that a task asks for are the fixtures commit in 1.3 and the `pnpm-lock.yaml` commits in 3.1 and 8.1. Other code commits belong to the task hook.
- Task completion notes record anything Kiro got wrong and the fix, for the `BUILD_LOG.md` entry of task 11.4.
- Nothing in this plan pushes to a remote.
