# Requirements Document

## Introduction

This feature records, in any workspace, which text in each source file Kiro's agent changed, and shows that record in Reveal Codes form. The Recorder is a command that Kiro's own hooks run at four events. At each event it compares every changed file with the last state it recorded and applies the difference to that file's Record through the existing Engine (`createDocument`, `apply`, `renderRecord`, `parseRecord`). The Record uses the same form as the Provenance Appendix: the Engine's full Reveal Codes rendering. Nothing about provenance is guessed from the text. Product principle 1 binds this spec: provenance is captured, never inferred, and where the Recorder cannot know, it says so.

A file gets a Record only when it first changes. Until then the Baseline_File holds the file's path, its SHA-256 digest and, where git is present, its Blob_Id, and the file is shown as `[PST]`. A Record starts from the file's text as of the baseline, as `[PST]`, with the first change applied to it. Because the Baseline_File stores no text, the Recorder must find the baseline text somewhere else when the first change arrives: in git, by Blob_Id, or in the Baseline_Cache, an ignored directory that holds starting text only for files that git cannot give back. Requirement 5 states where it looks and what it does when it finds nothing: it records the file's current text as `[PST]`, attributes that change to no one and logs `baseline_text_unavailable`. A Record never says that a whole file was written by the agent or by a person only because its starting text was lost. The consequence is stated in Decision 1.

Two windows are told apart by the hook events and never by looking at the text. A change that appears between Prompt Submit and Agent Stop, or between Pre Task Execution and Post Task Execution, is a change made while the agent was working. A difference found while no agent window was open is recorded as `[HUM]`. The legend for source files states only that. It does not claim that the agent's model wrote every character of an Agent_Change (a formatter or shell command the agent ran produces Agent_Changes too), it does not claim that a person typed an Outside_Change (it may be a paste, a `git pull`, or another tool), and it does not claim that the agent did not make it. In a session in which no prompt event fires, such as an IDE spec chat that runs tasks, only the task windows are the agent's, so an edit the agent makes between tasks is found while no window is open and is recorded as `[HUM]`. The Recorder counts the sessions in which that can have happened and the summary says so (Decision 20).

Windows are kept per session. The IDE and the CLI can run in one workspace at the same time, and so can two IDE chat tabs, so each window belongs to the `session_id` of the event that opened it, and an event of one session never closes another session's window. A change seen while any session's window is open is the agent's. The record cannot tell which concurrent session wrote such a change, so Requirement 3, criterion 21, gives a fixed rule for choosing the window it is attributed to (Decision 18).

The feature ships four things. The first is a new package `packages/provenance` (`@reveal-codes/provenance`) that holds the Recorder and the viewer. The second is a command, `reveal`, with three forms: a file with its codes inline, a summary, and a check. The third is a set of MCP tools that answer from the Record and return structured spans, not the model's memory. The fourth is a Power, `powers/provenance`, built and bundled the way `powers/citation-check` is, whose skill installs the whole thing in a workspace. A Power cannot carry hooks (see Decision 5), so the skill writes the hook file and says what it wrote.

This repository uses the feature from the start of the install task. Text that was in a file before the baseline is `[PST]`. The record starts on the day it was installed, and the documentation says so. Windows is not supported, and the README says so.

This spec changes no behavior of the web app, the Verifier, the exported filing format, or the Engine. The Engine keeps zero runtime dependencies. The commit-on-task hook keeps working.

Measurements taken on this repository on 2026-11-18, on an Apple M4 with Node 22.23.4, are the basis of the time limits below: 1,060 files are tracked and 7.0 million characters are in the 1,055 text files of 200,000 characters or fewer; hashing every such file takes 0.2 s and a cold `node` process that scans them takes 0.27 s in total; creating, rendering and parsing a Record for all 1,055 files takes 2.0 s in total, and the slowest file (`.kiro/specs/case-match/design.md`) takes 59 ms; one Engine `apply` on a 194,104-character file takes 2 ms. Under this spec only changed files get a Record, so the Record store is smaller than the 7.14 million characters that Records for all 1,055 files would have taken. A second measurement, taken the same day: the exact-byte Blob_Ids (as `git hash-object --no-filters` computes them) of all 1,064 tracked files are present in the object store, none is missing, no end-of-line conversion is in effect and the tree is clean, so the Baseline_Cache of this repository would hold 0 files and 0 bytes at a baseline taken on a clean tree; it grows only by the untracked or modified files at the baseline.

The answers to the questions that were open before design are recorded in the Decisions section at the end of this document. Each requirement that depends on an answer names it.

## Glossary

- **Engine**: `packages/engine`, `@reveal-codes/engine`. Its public entry points used here are `createDocument`, `apply`, `renderRecord`, `parseRecord`, `render` and `DEFAULT_RELABEL_THRESHOLD`.
- **Provenance_Package**: `packages/provenance`, `@reveal-codes/provenance`, the new package that holds the Recorder, the viewer, the summary, the check and the MCP server source.
- **Recorder**: the part of the Provenance_Package run by `provenance record <event>` that updates Records.
- **Reveal_Command**: the command line program `reveal` with the forms `reveal <file>`, `reveal --summary [path]` and `reveal --check [--strict]`, and the entry `reveal --record`.
- **Bundle**: the one file `provenance.mjs` that contains the Recorder, the Reveal_Command and the MCP server with no dependency to install.
- **Provenance_Power**: the directory `powers/provenance`, a Kiro Power that follows the Agent Plugins layout (`plugin.json`, `mcp.json`, `skills/`).
- **Setup_Skill**: the skill `skills/setup-provenance/SKILL.md` of the Provenance_Power.
- **Provenance_Tools**: the MCP tools exposed by the Bundle.
- **Workspace_Root**: the directory that holds the Record_Directory; the directory in which Kiro runs a command hook.
- **Record_Directory**: `.kiro/provenance/` under the Workspace_Root, committed (Decision 1). It holds the Records, the Baseline_File, the Sessions_File, the Ignore_File, the Bundle and the wrapper, and the files that its own `.gitignore` lists.
- **Record**: one file under `<Record_Directory>/records/<workspace-relative path>.reveal` that holds the Engine's full rendering (`renderRecord(doc, null, "full")`) of one tracked file. A Record exists only for a file that has changed since the baseline or that appeared after it. Its parsed Document text is the Recorded_Text.
- **Recorded_Text**: the `text` of the Document that `parseRecord` returns for a Record.
- **Baseline_File**: `<Record_Directory>/baseline.json`, the committed file that holds the time of the baseline and, for each Baseline_Entry, a workspace-relative path, the SHA-256 digest of the file's text at the baseline and, where git is present, the file's Blob_Id.
- **Baseline_Entry**: one path with its SHA-256 digest and, where git is present, its Blob_Id, in the Baseline_File. A Tracked_File has a Baseline_Entry only while it has no Record.
- **Blob_Id**: the git object id of a file's exact bytes, as `git hash-object --no-filters` computes it, so that end-of-line conversion and attribute filters do not change it.
- **Baseline_Cache**: the directory `<Record_Directory>/cache/`, ignored by git. Each file in it is named by the SHA-256 digest of its bytes and holds the starting text of a Tracked_File that git cannot give back (Requirement 5, criterion 19).
- **Unchanged_File**: a Tracked_File that has a Baseline_Entry, no Record, and a SHA-256 digest of its current text equal to the digest of the Baseline_Entry. The Reveal_Command shows it as `[PST]`.
- **Baseline_Text**: the text that a file had when the baseline was made. The Baseline_File never holds it; the Recorder gets it from git by Blob_Id, or from the Baseline_Cache, when a First_Change arrives (Requirement 5, criterion 5).
- **First_Change**: the first Agent_Change or Outside_Change that the Recorder finds at an event for a Tracked_File that has a Baseline_Entry and no Record.
- **Tracked_File**: a file that the Recorder keeps a Record or a Baseline_Entry for (Requirement 2).
- **Hook_Event**: one of `promptSubmit`, `agentStop`, `preTask`, `postTask`, named on the command line of the hook (these names are not the trigger names of the Hook_File; Requirement 8, criterion 1 maps them) (`provenance record <event>`) and never read from standard input, or `manual`, named by `reveal --record` and by the git pre-commit hook of this repository.
- **Session_Key**: the string that names one session in the Window_State: the value of the `session_id` field of the hook payload, or `_none` when the payload carries no usable `session_id` (Requirement 3, criterion 22). A `manual` event has no Session_Key.
- **Agent_Window**: the interval, within one session, from that session's `promptSubmit` event to its next `agentStop` event, or from its `preTask` event to its next `postTask` event, or to the closing that Requirement 3, criteria 8 and 23, state. Each Agent_Window belongs to exactly one Session_Key. Windows of one session nest as a stack, a task window above a `turn` window; windows of different sessions never nest.
- **Window_State**: the file `<Record_Directory>/state.json` that holds, for each Session_Key, the stack of that session's open windows (innermost last, possibly empty), the clock reading of that session's last event, the field `lastClosedBy` (`"postTask"`, `"agentStop"`, `"sweep"`, `"leftover"` or `null`: what closed the last window of that session, or `null` when the session has not closed one since it last opened one), the flag `promptSeen` (a `promptSubmit` event has fired in that session) and the flag `noPromptCounted` (that session has been counted in the Sessions_File), together with a count that numbers the openings of windows (the opening order), the cache of last-seen file digests, the clock reading of the last event of any session and the flag `noSessionIdLogged`, which records that `no_session_id` was logged during this lifetime of the file. A session entry may persist with no windows; the sweep of Requirement 3, criterion 23, drops an entry that has been idle for more than 12 hours.
- **Sessions_File**: the file `<Record_Directory>/sessions.json`, committed, of the form `{ "version": 1, "noPromptEventSessions": <count> }`. It holds the number of sessions counted by Requirement 3, criterion 26, and no Session_Key and no other session information.
- **Window_Run**: the name given to one Agent_Window, in the form `[<Task_Number> ]<Run_Label> <time>`: the Task_Number when the window has one, the Run_Label, and the UTC time at which the window opened, to the second. It contains no part of any Session_Key.
- **Run**: the Engine's Run_Id string given to every `AI` insertion of one Hunk of one Agent_Change. A Run name is the Window_Run, a `.`, and the Hunk number; the Hunk number is the digits after the last `.`.
- **Run_Label**: the title of a task, for a window opened by `preTask`: the value of the `task_name` field of the hook payload with its Task_Number removed (`Probe task one` for `1. Probe task one`), or the word `task` when no title remains; the word `turn` for a window opened by `promptSubmit`.
- **Task_Number**: the leading token of `task_name` that matches `\d+(\.\d+)*\.?` and is followed by a space or by the end of the string, written without its trailing `.` (`5.3`, `1`). It is absent when `task_name` has no such token, and for a `turn` window.
- **Agent_Change**: a difference between a file and its Record, or its Baseline_Text, that the Recorder finds at an event while an Agent_Window of any session is open, and that the attribution rule of Requirement 3, criterion 21, assigns to one such window. It carries that window's Window_Run and Run_Label.
- **Outside_Change**: a difference between a file and its Record, or its Baseline_Text, that the Recorder finds at an event while no Agent_Window of any session is open, that is, a difference found while no agent window was open. The term says nothing about who made the difference: a person, another tool, or the agent between task windows of a session that fires no prompt event (Decision 20).
- **No_Prompt_Session**: a session in which `agentStop` has fired and no `promptSubmit` has been seen, and which Requirement 3, criterion 26, counts.
- **Hunk**: one contiguous replacement in the line-based difference between the Recorded_Text, or the Baseline_Text, and the current file text, with offsets on line boundaries. The operation that the Recorder applies for a Hunk is the Hunk's remainder after the character trim of Requirement 4, criterion 15.
- **Origin**: one of `HUM`, `PST`, `AI`, `AI>HUM`, as defined in `product.md`.
- **Source_Legend**: the wording of the four Origins for source files (Requirement 9, criterion 3).
- **Untouched_Stretch**: a maximal run of consecutive `AI` characters in one Record, that is, an `AI` Span of the Record's canonical Document.
- **Changed_Characters**: for a file whose text differs from what is recorded, the sum of the lengths of the replacement texts and of the deleted texts of the Hunks (the Hunks as found, before the character trim); for a file with a Baseline_Entry whose Baseline_Text cannot be found, the length of the whole file text.
- **Fault_Log**: the file `<Record_Directory>/errors.log`.
- **Kiro_Ignore_File**: the file `.kiroignore` at the Workspace_Root. Kiro reads it to keep files from the agent; the Recorder reads it and never writes it.
- **Ignore_File**: the file `.kiro/provenance/ignore`, committed, which lists patterns for files that are not recorded. Setup writes it with comment lines only.
- **Hook_File**: the file `.kiro/hooks/0-provenance.json`. Its name begins with `0` so that it sorts, byte-wise, before `commit-on-task.json` (Requirement 8, criterion 5).
- **Size_Limit**: 200,000 UTF-16 code units of decoded text per file (Decision 11).
- **Hook_Deadline**: 20 seconds of wall-clock time for one Recorder run.
- **Stale_Record**: a file whose text differs from what the Record, or the Baseline_Entry, describes because the file changed after the last event.
- **Tampered_Record**: a Record that `parseRecord` rejects, or whose Document does not satisfy the Engine's own checks.
- **Structured_Span**: a JSON object `{ startLine, startColumn, endLine, endColumn, length, origin, run, taskNumber, taskTitle }` with 1-based lines, 1-based columns counted in UTF-16 code units, an end position that is exclusive, `run`, `taskNumber` and `taskTitle` equal to `null` for `HUM` and `PST`, and `taskNumber` equal to `null` for a window with no Task_Number; `taskTitle` is the Run_Label.
- **Probe**: the temporary hook that task 1 reruns (Requirement 18) and that records field names, field types, whether `session_id` is present, the form (absolute or workspace-relative) of `tool_input.path`, and the title fields `task_name` and `spec_name` of hook payloads, and nothing else; it records no `session_id` value, no `prompt` value and no path value.

## Requirements

### Requirement 1: Package, dependencies and boundaries

**User Story:** As a maintainer, I want the feature in one new package with explicit dependencies, so that the Engine, the web app, the Verifier and the export format stay as they are.

#### Acceptance Criteria

1. THE Provenance_Package SHALL live in `packages/provenance` under the name `@reveal-codes/provenance`.
2. THE Provenance_Package SHALL declare `@reveal-codes/engine` (`workspace:*`) as a runtime dependency and SHALL import the Engine only through its public entry point.
3. THE Provenance_Package SHALL declare as runtime dependencies exactly `@reveal-codes/engine` (`workspace:*`), `@modelcontextprotocol/sdk` and `zod`, the last two pinned to the exact versions that `packages/courtlistener-mcp` pins, and no other package; no text-difference library and no ignore-pattern library SHALL be added, because the line difference and the ignore matcher are hand-written; the Bundle SHALL contain both packages, and only the modules under `src/mcp/` SHALL import them (Requirement 12, criterion 1; Decision 19).
4. THE Engine SHALL keep zero runtime dependencies and SHALL receive no source change from this spec.
5. THE Provenance_Package SHALL contain the pure functions (difference, attribution, summary, check, view) in modules that import no `node:` module, and SHALL contain the file system, process, git and clock access in a small set of modules that receive them as injected values.
6. THE Provenance_Package SHALL use named exports only, plain data types and discriminated unions in place of classes, and no `any`.
7. THE Provenance_Package SHALL return `Result` values in place of thrown errors in every function except the command entry modules, SHALL limit each function to 40 lines or fewer and each module to 300 lines or fewer.
8. THE Provenance_Package SHALL reference `process.env` in exactly one module.
9. THE Provenance_Package SHALL make no network request and SHALL send no data anywhere.
10. THE Provenance_Package SHALL add no file under `apps/web`, `packages/verifier`, `packages/export` or `crew/sentinel`, and SHALL change no file there, except the two test edits of Requirement 19, criterion 2, which are the only changes to files under `packages/export` and `crew/sentinel`.
11. THE root `package.json` SHALL define the script `reveal` that runs the Reveal_Command from this repository's sources, and SHALL keep every existing script unchanged.

### Requirement 2: Which files are tracked

**User Story:** As a developer, I want the record to cover the text files that are part of my project and nothing else, so that the record stays small and holds nothing that does not belong in it.

#### Acceptance Criteria

1. WHERE the Workspace_Root is a git working tree and `git` is on the path, THE Recorder SHALL take the candidate files from `git ls-files --cached --others --exclude-standard`.
2. WHERE the Workspace_Root is not a git working tree or `git` is not on the path, THE Recorder SHALL take the candidate files from a walk of the Workspace_Root that skips the directories `.git`, `node_modules`, `dist`, `build`, `out`, `.next`, `coverage` and `target`, and SHALL apply no git ignore rule.
3. WHERE the Workspace_Root is a git working tree, THE Recorder SHALL exclude from the candidates every file that git ignores, including a tracked file that matches an ignore rule (the files that `git ls-files --cached --ignored --exclude-standard` lists).
4. THE Recorder SHALL exclude from the candidates every file under the Record_Directory.
5. THE Recorder SHALL exclude from the candidates the lockfiles `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `Cargo.lock`, `Gemfile.lock`, `poetry.lock`, `composer.lock`, `go.sum` and every file whose name ends in `.lock`.
6. THE Recorder SHALL exclude from the candidates every file whose name ends in `.min.js`, `.min.css` or `.map`, and every file under a directory named `dist`, `build`, `out`, `.next`, `coverage` or `target`.
7. THE Recorder SHALL exclude from the candidates every file whose name is `.env` or begins with `.env.`, or ends in `.pem`, `.key`, `.p12` or `.pfx`, or begins with `id_rsa` or `id_ed25519`.
8. THE Recorder SHALL exclude from the candidates every file that matches a pattern of the Kiro_Ignore_File or of the Ignore_File, each file read and evaluated on its own, so that a file is excluded when either file excludes it, and a `!` pattern in one file SHALL never re-include a file that the other file, git or the built-in rules of criteria 4 to 7 exclude (Decision 16, Decision 19).
9. THE Recorder SHALL parse the Kiro_Ignore_File and the Ignore_File with the full gitignore pattern syntax, as the gitignore documentation defines it for a `.gitignore` at the Workspace_Root: blank lines and `#` comment lines; a backslash that escapes `#`, `!`, a space or any other character; trailing spaces ignored unless escaped; `!` negation, where the last matching pattern decides; `*`, `?` and bracket classes with ranges, negation and POSIX class names; `**` as a leading `**/`, a trailing `/**` and an inner `/**/`; a trailing `/` that matches directories only; a pattern with no `/` other than a trailing one that matches at any depth, and a pattern with any other `/` that is anchored at the Workspace_Root; and the rule that a file cannot be re-included while a directory above it is excluded; THE parser SHALL be a hand-written, tested matcher in the Provenance_Package that adds no dependency, SHALL read no nested and no global ignore file, and SHALL treat a line that gitignore treats as matching nothing (for example an unterminated bracket class) as matching nothing (Decision 19).
10. IF a candidate file is larger than the Size_Limit after decoding, THEN THE Recorder SHALL skip the file and SHALL write one line naming the file and the reason `over_limit` to the Fault_Log once for each file, and again only after its size or modification time has changed, and not at every later event.
11. IF a candidate file contains a NUL byte or its bytes are not valid UTF-8, THEN THE Recorder SHALL skip the file as a binary file and SHALL write no line to the Fault_Log for it.
12. WHEN a file that has a Record or a Baseline_Entry becomes excluded, over the Size_Limit or binary, or is deleted, THE Recorder SHALL delete its Record and its Baseline_Entry, and the Baseline_Cache file named by that entry's digest when no other Baseline_Entry has that digest, at the next event.
13. WHEN a file that has neither a Record nor a Baseline_Entry stops being excluded, or falls to the Size_Limit or below, THE Recorder SHALL treat it as a file that appeared at that event (Requirement 5, criteria 7 and 8).
14. THE Recorder SHALL treat a symbolic link as absent and SHALL never follow it.

### Requirement 3: The windows and the events

**User Story:** As a developer, I want the agent's changes told apart from mine by Kiro's own events, so that the record never depends on a guess about the text.

#### Acceptance Criteria

1. WHEN the Recorder is started as `provenance record <event>` with `<event>` equal to `promptSubmit`, `agentStop`, `preTask`, `postTask` or `manual`, THE Recorder SHALL treat that name as the Hook_Event and SHALL read no event name from standard input.
2. WHEN the Hook_Event is `promptSubmit` in session S, THE Recorder SHALL attribute every difference found by the rule of criterion 21, then open an Agent_Window of Run_Label `turn` in S only and in no other session, and SHALL set `promptSeen` in the entry of S.
3. WHEN the Hook_Event is `preTask` in session S and S has no open Agent_Window, THE Recorder SHALL attribute every difference found by the rule of criterion 21, then open an Agent_Window in S only whose Run_Label is the task title.
4. WHEN the Hook_Event is `preTask` in session S and S has an open Agent_Window, THE Recorder SHALL record every difference found as an Agent_Change of S's innermost open window, then open an Agent_Window in S only whose Run_Label is the task title, above S's innermost open window.
5. WHEN the Hook_Event is `postTask` in session S, THE Recorder SHALL attribute every difference found by the rule of criterion 21, then close S's innermost open window, if S has one, leave open the window of S below it, if any, and leave every window of every other session open; WHEN that closing leaves S with no open window, THE Recorder SHALL set `lastClosedBy` of S to `"postTask"` and SHALL keep the entry of S in the Window_State with an empty stack (Decision 20).
6. WHEN the Hook_Event is `agentStop` in session S, THE Recorder SHALL attribute every difference found by the rule of criterion 21, then close every open window of S, set `lastClosedBy` of S to `"agentStop"` and keep the entry of S, and leave every window of every other session open.
7. IF a `postTask` or `agentStop` event arrives in a session that has no open Agent_Window, THEN THE Recorder SHALL attribute every difference found by the rule of criterion 21, which yields an Outside_Change only when no window of any session is open, and SHALL write one line naming the event and the reason `no_open_window` to the Fault_Log, except that an `agentStop` event that arrives in a session whose entry has `lastClosedBy` equal to `"postTask"` (the last window of that session was closed by that session's own `postTask`) SHALL write no line; after any `agentStop` the entry of that session has `lastClosedBy` equal to `"agentStop"`, so that a second `agentStop` writes `no_open_window` (Decision 20).
8. IF a `promptSubmit` event arrives in a session S that already has an open Agent_Window, THEN THE Recorder SHALL close every open window of S and no window of another session, write one line naming the event and the reason `window_left_open` to the Fault_Log, attribute every difference found by the rule of criterion 21 over the windows that remain open, and open a new `turn` window in S (Decision 7, Decision 18).
9. WHEN the Hook_Event is `manual` and no Agent_Window of any session is open, THE Recorder SHALL record every difference found as an Outside_Change and SHALL open no window (Decision 2).
10. WHEN the Hook_Event is `manual` and an Agent_Window of any session is open, THE Recorder SHALL attribute every difference found by the rule of criterion 21, which for a `manual` event selects the most recently opened innermost window among all sessions, and SHALL leave every window of every session open, so that a commit made in the middle of a window does not turn the agent's text into `[HUM]` (Decision 2).
11. THE Recorder SHALL name each Window_Run so that it is unique among the windows of the Record_Directory and contains the Task_Number when the window has one, the Run_Label, and the UTC time at which its window opened, to the second, and SHALL include no part of any prompt text and no part of any Session_Key.
12. THE Recorder SHALL name each Run as the Window_Run, a `.`, and a Hunk number, where the Hunk number is 1 plus the count of Runs of that Window_Run that already exist in the same Record, taken in ascending order of file offset for the Hunks of one event (Decision 8).
13. WHEN a `preTask` or `postTask` payload on standard input carries the field `task_name` as a non-empty string, THE Recorder SHALL collapse every run of whitespace and every control character (Unicode general category Cc: the C0 controls, DEL and the C1 controls) to one space, trim it, split off its Task_Number, and use the rest, cut to 80 characters, as the Run_Label; so `5.3 Build the view` gives the Task_Number `5.3` and the Run_Label `Build the view`, `1. Probe task one` gives `1` and `Probe task one`, and `Build the view` gives no Task_Number; THE Recorder SHALL keep the Task_Number and the Run_Label as separate values on the window, SHALL put both into the Window_Run, and SHALL store both on the Run through the Run name (Requirement 3, criterion 12), so that the viewer and the tools can say `written in task 5.3 Build the view` (Requirement 10, criterion 11; Decision 4; Decision 19).
14. IF a `preTask` payload carries no `task_name`, or a `task_name` that is empty after it is collapsed, or a `task_name` that holds only a Task_Number, THEN THE Recorder SHALL use the word `task` as the Run_Label, and SHALL keep the Task_Number when `task_name` held one and have none otherwise; THE Recorder SHALL read no payload field other than those that criterion 16 lists to find a label.
15. THE Recorder SHALL read standard input for at most 1.5 seconds and SHALL continue with an empty payload when standard input is not closed, is empty, is not valid JSON, or is larger than 1 MiB.
16. THE Recorder SHALL read from the hook payload only the fields `session_id`, `cwd`, `task_name`, `spec_name` and `task_success` (`task_name` is the title of a spec task, which is spec text and not the person's prompt, and the Task_Number and the Run_Label come from it), SHALL discard every other field, SHALL never read, store or log the field `prompt` (the Recorder may parse the JSON of the payload but SHALL discard that field without copying it), and SHALL use only `session_id` and `cwd` when handling `promptSubmit`, because nothing else is needed; the `UserPromptSubmit` payload carries `session_id`, `hook_event_name`, `cwd` and `prompt` on the IDE and on the CLI alike (Decision 4).
17. THE Recorder SHALL write the Window_State to disk by writing a temporary file in the Record_Directory and renaming it over `state.json`.
18. WHEN two Recorder processes run at the same time in one Workspace_Root, THE Recorder SHALL take a lock in the Record_Directory before it reads or writes any Record, and SHALL give up after 5 seconds, write one line with the reason `lock_timeout` to the Fault_Log and exit with status 0 without changing any Record; a lock file that is older than 30 seconds SHALL be removed before the wait, so that a crashed Recorder does not make every later event time out (Decision 19).
19. WHEN the payload carries `spec_name`, THE Recorder SHALL use at most the name of the directory that contains that `tasks.md` as the name of the spec, and SHALL store in no Record, Baseline_File, Window_State or Fault_Log line any absolute path from the payload; a path from the payload SHALL be stored only as a workspace-relative path or as that directory name.
20. THE Recorder SHALL not determine whether it runs in the IDE, the CLI or the Web, SHALL read no `KIRO_*` or `VSCODE_*` environment variable to decide anything, and SHALL behave identically on every surface, because those variables differ between runs on one surface; fixtures are labelled by how they were captured and never by inspecting the environment (Decision 4).
21. WHEN the Recorder finds a difference at an event, THE Recorder SHALL attribute it, using the windows that are open when the event starts after the closings of criteria 8 and 23 and before any opening or closing that the event itself makes, to the first of these that applies: (a) the innermost open window of the session of the event, if that session has one; (b) otherwise, if a session other than the session of the event has an open window, the window that was opened most recently by the opening order in the Window_State among the innermost open windows of those other sessions; (c) otherwise no window, and the difference is an Outside_Change. A `manual` event has no session, so its attribution begins at (b) over all sessions. WHEN a window is selected, THE Recorder SHALL record the difference as an Agent_Change that carries the Window_Run and Run_Label of that window (Decision 18).
22. IF a hook payload carries no `session_id`, or carries a `session_id` that is not a string or is an empty string, THEN THE Recorder SHALL use the Session_Key `_none` for that event, so that the windows of such events open and close as a pair in one session, SHALL write one line with the reason `no_session_id` to the Fault_Log the first time it does so while `state.json` does not have the flag `noSessionIdLogged`, and SHALL set that flag in `state.json`, so that the line is written once for each lifetime of `state.json` and not at every event, a `state.json` that is absent, unreadable or replaced starting a new lifetime; and SHALL never infer a Session_Key from the environment, the parent process, the surface or any other source (Decision 18, Decision 19).
23. WHEN an event of any session starts, THE Recorder SHALL, before it attributes any difference, close every open window of every session whose last event is more than 12 hours (43,200 seconds) before the clock reading of this event, the current event not counted as that last event, and SHALL write one line naming the reason `window_left_open` to the Fault_Log for each window it closes; a window closed this way SHALL select no difference at this event; the sweep SHALL also drop the entry of every session whose last event is more than 12 hours before this event, whether or not that session still had a window, and SHALL write no line for an entry that had no window, because a session entry persists after its last window closes only for the purposes of criteria 7 and 26 and is not otherwise kept (Decision 18, Decision 20).
24. THE Recorder SHALL change at an event only the entry of the session of that event (its stack of windows, `lastClosedBy`, `promptSeen` and `noPromptCounted`), except for the closings and the dropped entries of criterion 23, and SHALL record the clock reading of the event as the last event of that session in the Window_State; WHEN an event opens a window in a session, THE Recorder SHALL set `lastClosedBy` of that session to `null`.
25. THE Recorder SHALL store a Session_Key only in the Window_State, and SHALL write no Session_Key to any Record, the Baseline_File, the Fault_Log, a Window_Run, a Run or standard output.
26. WHEN an `agentStop` event arrives in session S, the entry of S has neither `promptSeen` nor `noPromptCounted`, and at least one difference that the event found is attributed by criterion 21 to no window (it is an Outside_Change), THE Recorder SHALL write one line with the reason `no_prompt_events` to the Fault_Log, set `noPromptCounted` in the entry of S, and add 1 to `noPromptEventSessions` in the Sessions_File (criterion 27); THE Recorder SHALL do this at most once for one session entry, and SHALL never count a session whose entry has `promptSeen`. A session that ran spec tasks and fired no prompt event (an IDE Specs-panel task session: `preTask`, tool calls, `postTask`, `agentStop`) is counted under the same condition and no other: it is counted only when its `agentStop` found differences outside any window, because a session in which nothing was found outside a window lost nothing that the Recorder could have recorded differently. The rule counts a session and changes no Record and no attribution (Decision 20).
27. THE Recorder SHALL write the Sessions_File by a temporary file and a rename, only at the event that sets `noPromptCounted` and at the baseline when the file is absent (Requirement 6, criterion 7), SHALL hold in it the count and no Session_Key, and SHALL leave its bytes unchanged at every other event, so that running the same event again changes nothing (Requirement 16, Property 4). IF the Sessions_File cannot be parsed, THEN THE Recorder SHALL leave it as it is, write one line with the reason `bad_sessions` to the Fault_Log, and neither add to a count nor set `noPromptCounted`. Because `state.json` is not committed, a `state.json` that is absent or replaced forgets which sessions were counted, and a session that is still running may be counted again; the count is then an upper bound on the number of such sessions, and the README says so (Decision 20).

### Requirement 4: Applying a difference through the Engine

**User Story:** As a developer, I want every change applied to the record by the Engine's own operations, so that the record means what the Engine says it means and no second implementation of provenance exists.

#### Acceptance Criteria

1. THE Recorder SHALL decode a file as UTF-8 and SHALL keep a leading byte order mark, carriage returns and every other character in the text unchanged.
2. WHEN a tracked file's text differs from its Recorded_Text, or from its Baseline_Text on its First_Change, THE Recorder SHALL compute a line-based difference whose Hunks are replacements `[from, to) → text` over that earlier text, with every offset on a line boundary of that earlier text.
3. THE Recorder SHALL give each Hunk of an Agent_Change its own Run (Requirement 3, criterion 12) and SHALL apply the Hunks to the Document from the highest offset to the lowest, each through one Engine `apply` call of kind `insert`, `delete` or `replace`, over the Hunk's remainder after the trim of criterion 15.
4. WHEN an Agent_Change inserts text, THE Recorder SHALL give the insertion the origin `AI`, the Run of its Hunk, and the clock reading of the event as timestamp.
5. WHEN an Outside_Change inserts text, THE Recorder SHALL give the insertion the origin `HUM` and the clock reading of the event as timestamp.
6. WHEN an Outside_Change deletes text, THE Recorder SHALL call `apply` with a `delete` whose actor is `HUM`, or with a `replace` whose provenance origin is `HUM`.
7. WHEN an Agent_Change deletes text, THE Recorder SHALL call `apply` with a `delete` whose actor is `AI`, or with a `replace` whose provenance origin is `AI`.
8. THE Recorder SHALL pass no `relabelThreshold` to `apply`, so that the Engine's default of `DEFAULT_RELABEL_THRESHOLD` (0.4) decides when a Run becomes `AI>HUM`; because each Run is one Hunk, the Engine relabels one Hunk's text and not a whole window (Decision 8).
9. THE Recorder SHALL create no `AI>HUM` Span itself; a Span of origin `AI>HUM` SHALL appear in a Record only as the Engine's own relabelling of a Run.
10. THE Recorder SHALL leave every character outside the remainder of every Hunk (the characters that no applied operation replaces or deletes) with the origin, Run and timestamp it had in the Record, or `PST` and the baseline time when the earlier text is a Baseline_Text.
11. IF an `apply` call returns an error, THEN THE Recorder SHALL leave that file's Record and Baseline_Entry as they were, write one line with the file path and the error kind to the Fault_Log, and continue with the next file.
12. THE Recorder SHALL write a Record only when the Document's `text` equals the file text that was read, and WHEN the file's modification time changed while the Recorder updated that file, THE Recorder SHALL keep the previous Record and Baseline_Entry and leave the file for the next event.
13. WHILE the time since the Recorder started is above the Hook_Deadline, THE Recorder SHALL stop starting new files, leave every unprocessed file's Record and Baseline_Entry as they were, and write one line with the reason `deadline_reached` followed by `:` and the number of files not reached to the Fault_Log (Decision 19).
14. WHEN the Engine's citation layer finds citation-like text in a source file, THE Recorder SHALL keep that layer in the Record unchanged and SHALL set no verification result, override or quote check.
15. THE Recorder SHALL keep every offset of the line difference on a line boundary of the earlier text (criterion 2), and, before it applies a Hunk, SHALL trim the common prefix and then the common suffix of the Hunk's old text and new text, by UTF-16 code unit, so that a boundary never falls between a high and a low surrogate or between a carriage return and the line feed after it (it SHALL move the boundary back to keep the pair whole), and the suffix trim SHALL NOT overlap the prefix; THE Recorder SHALL give the Engine one `replace` from the earlier offset plus the prefix to the earlier end offset minus the suffix, whose text is the remaining new text, with no `relabelThreshold` and no change to the Engine (Decision 21).
16. WHEN a Hunk's old text and new text are equal after the trim, THE Recorder SHALL produce no operation for it and SHALL give it no Run number; a Hunk whose remainder only deletes SHALL take no Run number, as before.

### Requirement 5: The record store and the baseline file

**User Story:** As a developer, I want a record only for files that changed, and a small committed baseline for the rest, so that the record store stays small and still reproduces every file.

#### Acceptance Criteria

1. THE Recorder SHALL keep at most one Record per Tracked_File at `<Record_Directory>/records/<workspace-relative path>.reveal`, with `/` as the separator on every platform, and SHALL keep a Baseline_Entry only for a Tracked_File that has no Record.
2. THE Recorder SHALL write each Record as `renderRecord(document, null, "full").text`, so that `parseRecord` of a Record returns the Document it was made from.
3. THE Recorder SHALL write each Record, and the Baseline_File, by writing a temporary file in the same directory and renaming it over the target, so that a killed process leaves either the old file or the new one.
4. THE Recorder SHALL write the Baseline_File as JSON with one Baseline_Entry per line, ordered by path, so that two branches that change different entries merge without conflict.
5. WHEN a First_Change is found, THE Recorder SHALL obtain the Baseline_Text in this order and in no other way: first, WHERE `git` is present and the Baseline_Entry has a Blob_Id, the bytes that `git cat-file blob <Blob_Id>` returns, if the SHA-256 digest of those bytes equals the digest of the Baseline_Entry, with no limit on how many commits ago the file changed and with no walk of the history, because a blob is addressed by its id; second, the Baseline_Cache file `<Record_Directory>/cache/<digest>` named by the digest of the Baseline_Entry, if the SHA-256 digest of its bytes equals its name; third, no text (Decision 1, Decision 19).
6. WHEN the Baseline_Text is found, THE Recorder SHALL create the Record by `createDocument(baselineText, baselineTime)`, so that every character has origin `PST`, then apply the Hunks of Requirement 4, then delete the Baseline_Entry in the same event, and the Baseline_Cache file named by its digest when no other Baseline_Entry has that digest.
7. IF the Baseline_Text is not found, THEN THE Recorder SHALL create the Record by `createDocument(currentFileText, clock)`, so that every character of the current file text has origin `PST` with the clock reading of the event as its timestamp, SHALL apply no Hunk, SHALL attribute the change to no window and to no one, SHALL delete the Baseline_Entry (and its Baseline_Cache file by the rule of criterion 6), and SHALL write one line with the file path and the reason `baseline_text_unavailable` to the Fault_Log; THE Recorder SHALL never record a whole file with origin `AI` or `HUM` because its Baseline_Text could not be found, and SHALL attribute later changes to that file as Requirement 3 states (Decision 1, Decision 19).
8. WHEN a Tracked_File appears that has neither a Record nor a Baseline_Entry and the attribution rule of Requirement 3, criterion 21, selects a window at the event, THE Recorder SHALL create its Record by `createDocument("", clock)` followed by an `AI` insertion of the whole file text with the Run `<Window_Run>.1`.
9. WHEN a Tracked_File appears that has neither a Record nor a Baseline_Entry and the attribution rule of Requirement 3, criterion 21, selects no window at the event, THE Recorder SHALL create its Record by `createDocument("", clock)` followed by a `HUM` insertion of the whole file text.
10. WHEN a Tracked_File that has a Record or a Baseline_Entry is gone at an event, THE Recorder SHALL delete its Record or its Baseline_Entry, SHALL delete the Baseline_Cache file named by that entry's digest when no other Baseline_Entry has that digest, and SHALL delete the directories under `records/` that the deletion leaves empty.
11. WHEN, at one event, a Record's file is gone and a new file without a Record has exactly the same decoded text and is not empty, THE Recorder SHALL move the Record to the new path and SHALL treat the move as a rename that changes no span.
12. WHEN, at one event, a Baseline_Entry's file is gone and a new file that has neither a Record nor a Baseline_Entry has a SHA-256 digest equal to that Baseline_Entry's digest, THE Recorder SHALL change only the path of that Baseline_Entry and SHALL create no Record.
13. THE Recorder SHALL treat a change of both name and content, or a rename whose text matches more than one gone file, as a deletion followed by a creation.
14. IF a Record cannot be parsed by `parseRecord`, THEN THE Recorder SHALL leave the Record file as it is, write one line with the file path and the reason `tampered_record` to the Fault_Log, and SHALL not write a new Record for that path until the Record has been removed by a person.
15. IF the text of a Tracked_File differs from what its Record or Baseline_Entry describes at an event, THEN THE Recorder SHALL record the difference at that event as Requirement 3 states, so that, after the event, the Recorded_Text equals the file text or, for a file with a Baseline_Entry, the digest of the file text equals the digest of the Baseline_Entry.
16. THE Recorder SHALL keep in `state.json`, per file, the size, modification time and SHA-256 digest of the text it last recorded or checked, and SHALL skip a file whose size and modification time match; WHEN `state.json` is absent or unreadable, THE Recorder SHALL compare every file with its Record or Baseline_Entry.
17. THE Recorder SHALL treat a `state.json` that cannot be parsed as absent, SHALL write one line with the reason `bad_state` to the Fault_Log, and SHALL close every Agent_Window of every session that it held.
18. IF the Baseline_File cannot be parsed, THEN THE Recorder SHALL leave it as it is, write one line with the reason `bad_baseline` to the Fault_Log, and SHALL create no Record that depends on a Baseline_Entry until a person has repaired or removed the Baseline_File.
19. THE Baseline_Cache SHALL hold starting text only for a Tracked_File that git cannot give back at the baseline: WHERE the Workspace_Root is not a git working tree or `git` is not on the path, for every Baseline_Entry; WHERE it is, for each Baseline_Entry whose Blob_Id is not in the object store (an untracked file, or a file whose bytes differ from every blob that git holds because it was modified at the baseline); THE Recorder SHALL write each cache file by a temporary file and a rename, SHALL name it by the SHA-256 digest of its bytes so that identical texts share one file, SHALL list `cache/` in the `.gitignore` of the Record_Directory, SHALL never read the cache for a file that has a Record, and SHALL delete a cache file when no Baseline_Entry has its digest (Decision 1, Decision 19).

### Requirement 6: The baseline

**User Story:** As a developer, I want the record to start from a plain baseline, so that text that was already in a file is never described as written by anyone.

#### Acceptance Criteria

1. WHEN `provenance baseline` runs and a Tracked_File has neither a Record nor a Baseline_Entry, THE Recorder SHALL add a Baseline_Entry with the SHA-256 digest of the file's current text and, WHERE git is present, its Blob_Id, SHALL write the file's text to the Baseline_Cache where Requirement 5, criterion 19, says the cache holds it, and SHALL create no Record.
2. WHEN `provenance baseline` runs and a Tracked_File has a Record or a Baseline_Entry, THE Recorder SHALL leave that Record and that Baseline_Entry unchanged.
3. THE Recorder SHALL write the clock reading of the baseline once into the Baseline_File as `at`, in the form `{ "version": 1, "at": "<ISO 8601 UTC>", "files": { ... } }`, and SHALL leave `at` unchanged on a second run.
4. WHEN `provenance baseline` finishes, THE Recorder SHALL print one line to standard output that gives the number of Baseline_Entries added and the number of files skipped (the candidate files that were not baselined because they are over the Size_Limit, binary or unreadable; a file that already has a Record or a Baseline_Entry is not counted), and no other output; this is the only command that prints on success besides the Reveal_Command forms.
5. THE Recorder SHALL finish the baseline of this repository (1,055 files) in 10 seconds or less on the hardware named in the Introduction.
6. THE Recorder SHALL compute the Blob_Id of every file that it baselines as `git hash-object --no-filters` computes it over the file's exact bytes, in one batched `git` call for all files and not one call for each file, SHALL write it to the Baseline_Entry only WHERE git is present, SHALL determine which Blob_Ids are in the object store with one batched `git cat-file --batch-check` call, and SHALL use the Blob_Id for no purpose other than finding the Baseline_Text.
7. WHEN `provenance baseline` runs and the Sessions_File does not exist, THE Recorder SHALL write it with `{ "version": 1, "noPromptEventSessions": 0 }` by a temporary file and a rename; WHEN it exists, THE Recorder SHALL leave it unchanged, so that a second run changes no byte and so that the `git add` of the pre-commit hook of Requirement 14, criterion 6, always names an existing file (Decision 20).

### Requirement 7: Hooks that are invisible and cannot break a session

**User Story:** As a developer, I want the hooks to cost me nothing and never stop my work, so that I can leave recording on.

#### Acceptance Criteria

1. WHEN `provenance record <event>` runs, THE Recorder SHALL write nothing to standard output.
2. WHEN `provenance record <event>` runs, THE Recorder SHALL write nothing to standard error.
3. THE Recorder SHALL exit with status 0 for every input and every failure, including an unknown event name, a missing Record_Directory, a corrupt Record, an unreadable file, a full disk, an uncaught exception and an unhandled rejection.
4. IF any fault occurs while the Recorder runs, THEN THE Recorder SHALL append one line to the Fault_Log that holds the ISO 8601 time, the Hook_Event, the file path when one applies, and a reason code, and SHALL include in the line no file text, no prompt text and no payload field.
5. IF the Fault_Log cannot be written, THEN THE Recorder SHALL discard the line and still exit with status 0.
6. WHEN the Fault_Log is larger than 256 KiB, THE Recorder SHALL replace it with its last 128 KiB before it appends.
7. WHEN `provenance record promptSubmit` runs on this repository with no file changed since the last event, THE Recorder SHALL finish in 0.5 seconds or less, measured on the hardware named in the Introduction, because the event sits in front of every prompt (Decision 15).
8. WHEN `provenance record <event>` runs for any other event on this repository with no file changed since the last event, THE Recorder SHALL finish in 1.5 seconds or less, and WHEN it runs with no `state.json`, it SHALL finish in 5 seconds or less, both measured on the hardware named in the Introduction.
9. THE design SHALL report the typical time (the median of at least 20 runs) of a `promptSubmit` event with no change on this repository, and `BUILD_LOG.md` SHALL repeat it; the measured floor of a node hook that reads standard input and runs three git commands is 33 to 50 ms per event, typically 35 ms, on both surfaces (Decision 15), and the Recorder's own time SHALL be measured once it is built and reported against that floor.
10. THE Recorder SHALL end its own run no later than the Hook_Deadline plus 2 seconds, which is below the 60-second default timeout of a Kiro command hook.
11. THE Hook_File SHALL set `"timeout": 30` (seconds) on each hook, and SHALL contain no `timeout_ms` field, because the IDE honours `timeout` and ignores `timeout_ms` (Decision 16).

### Requirement 8: The hook file and the order with commit-on-task

**User Story:** As a developer, I want the recorder's hooks to sit beside my existing hooks without changing them, so that the commit after a spec task still works and contains the record of that task.

#### Acceptance Criteria

1. THE Hook_File SHALL be the file `.kiro/hooks/0-provenance.json` and SHALL define exactly four command hooks: trigger `UserPromptSubmit` running `provenance record promptSubmit`, trigger `Stop` running `provenance record agentStop`, trigger `PreTaskExec` running `provenance record preTask`, and trigger `PostTaskExec` running `provenance record postTask`; the Hook_Event names on the command line stay `promptSubmit`, `agentStop`, `preTask` and `postTask` (Decision 4).
2. THE command of each hook SHALL run the Bundle with `node` from the Workspace_Root, SHALL redirect standard output and standard error of the process to `/dev/null`, and SHALL end in `|| true`, so that a missing `node` or a missing Bundle leaves exit status 0.
3. THE Hook_File SHALL define no hook for any trigger other than the four of criterion 1 (Decision 6).
4. WHEN a spec task completes in a workspace that has both the Hook_File and `commit-on-task.json`, THE Recorder SHALL have finished recording the task before `scripts/commit-task.sh` runs `git add -A`, so that the Records changed by the task are in the task's commit.
5. THE spec SHALL change no line of `scripts/commit-task.sh`, and an example test SHALL assert that the file name of the Hook_File sorts before `commit-on-task.json` byte-wise, because two `PostTaskExec` hooks in different files ran in file-name order in the IDE (Decision 13).
6. THE design and the `README.md` SHALL state that the Records land in the task's commit because the IDE runs hooks of one trigger in file-name order, and SHALL state that the CLI fired no `PreTaskExec` or `PostTaskExec` in the capture of task 1.2 (asked in chat to execute a spec task, it wrote the file in an ordinary turn), so that no hook order can be measured on the CLI, `commit-on-task` does not run there, and the Records of CLI work are committed by the pre-commit hook or by the next commit that includes them (Requirement 18, criterion 5; Decision 13).
7. THE Hook_File SHALL leave `.kiro/hooks/commit-on-task.json` and every other existing hook file unchanged, except the five test hooks that Requirement 19 changes; this is the one exception to the rule that this spec changes no existing hook.
8. WHEN the Record_Directory is under `.kiro/`, THE scope that `scripts/commit-task.sh` derives for a commit SHALL be the same as without the Record files, because that script ignores paths under `.kiro/`.

### Requirement 9: `reveal <file>`, the file with its codes inline

**User Story:** As a developer, I want to see a source file with provenance codes inline in my terminal, so that I can see who changed what, in the pane's look.

#### Acceptance Criteria

1. WHEN `reveal <file>` runs and the file has a Record whose Recorded_Text equals the file text, THE Reveal_Command SHALL print, under a header of one line that names the file and the legend of criterion 3, the provenance codes of the Record's Document with the file's text.
2. WHEN `reveal <file>` runs and the file is an Unchanged_File, THE Reveal_Command SHALL print the header and the whole file text as one `[PST]` code and its text, read from the file.
3. THE Reveal_Command SHALL print the Source_Legend as these four items, in this order: `[AI:<run>]` "changed while the agent was working, with the run it belongs to"; `[AI>HUM:<run>]` "agent text in a run that the Engine counts as edited while no agent window was open"; `[HUM]` "changed while no agent window was open; typing, pasting and other tools are not told apart"; `[PST]` "already in the file when recording started; origin not recorded".
4. THE Reveal_Command SHALL print only the provenance codes `[AI]`, `[AI>HUM]`, `[HUM]` and `[PST]` of the Engine's rendering, and SHALL omit the citation, quote, reference and override codes that the Engine's citation layer adds to source text (Decision 10).
5. WHERE the output is a terminal that reports 24-bit color through `COLORTERM` set to `truecolor` or `24bit` and `NO_COLOR` is not set, THE Reveal_Command SHALL print each code and its text in the Pane's colors from `product.md`: pane body background `#0F2766` with text `#E8ECF6`, `HUM` `#E8ECF6`, `PST` `#F5D98B`, `AI` `#A6D4F7`, `AI>HUM` `#D7C6F5`, header title `#FFFFFF`, legend `#BAC4E2`, and SHALL print the file's text without the Engine's escaping and with the replacement of criterion 13, so that the codes are told apart from the text by color (Decision 10).
6. WHERE the output is a terminal that reports 256 colors in `TERM` and not 24-bit color, THE Reveal_Command SHALL print the same colors mapped to the nearest entries of the 256-color palette, with the file's text unescaped and with the replacement of criterion 13.
7. WHERE the output is not a terminal, or `NO_COLOR` is set, or `TERM` is `dumb`, THE Reveal_Command SHALL print plain text with no escape sequence and with the Engine's escaping of `\`, `[` and `]` in the file's text and with the replacement of criterion 13, so that a code is never confused with text.
8. FOR ALL files, removing every ANSI escape sequence from the colored output SHALL give the plain-text output with the Engine's escaping removed from the file's text characters, that is, `unescape(plain)` equals `strip(colored)`, where `unescape` removes the escapes from text characters only and leaves codes, header and legend as they are; both outputs carry the replacement of criterion 13.
9. IF the file has no Record and is not an Unchanged_File, THEN THE Reveal_Command SHALL print one line that says the file is not recorded and the reason (`not_tracked`, `over_limit`, `binary`, `ignored`, or `no_record`), and SHALL exit with status 1, where `no_record` means a tracked file that has neither a Record nor a Baseline_Entry, and a file with a Baseline_Entry whose digest differs is a Stale_Record under criterion 10.
10. IF the file is a Stale_Record, THEN THE Reveal_Command SHALL print as the first line the statement that the file changed after the last recorded event, with the number of Changed_Characters that are not yet recorded and the command `reveal --record`, SHALL print the Record as recorded after that line when a Record exists, SHALL print no code after that line when the file has only a Baseline_Entry, SHALL never present the output as current, and SHALL exit with status 0.
11. IF the Record is a Tampered_Record, THEN THE Reveal_Command SHALL print one line that names the file and the reason `tampered_record`, and SHALL exit with status 1.
12. THE Reveal_Command SHALL print nothing to standard error on success.
13. THE Reveal_Command SHALL replace, in the file's text and in the colored and the plain output alike, every C0 control character other than line feed and tab with the one UTF-16 code unit that is U+2400 plus its code (U+241B for ESC, U+240D for carriage return), DEL with U+2421, and every C1 control character (U+0080 to U+009F) with U+FFFD, so that no escape sequence in a file reaches the terminal and no line, column or length changes (Decision 19).

### Requirement 10: `reveal --summary [path]`

**User Story:** As a developer, I want a summary of what the agent wrote that no person has changed since, so that I know which parts nobody has read by editing them.

#### Acceptance Criteria

1. WHEN `reveal --summary` runs with no path, THE Reveal_Command SHALL summarize every Record and every Unchanged_File; WHEN it runs with a path to a file or a directory, THE Reveal_Command SHALL summarize the Records and Unchanged_Files under that path.
2. THE Reveal_Command SHALL print, per file and in total, the number of characters of each Origin (`AI`, `AI>HUM`, `HUM`, `PST`) and its share of the file's characters as a percentage with one decimal, the four shares summing to 100.0 within rounding, and SHALL count every character of an Unchanged_File as `PST`.
3. THE Reveal_Command SHALL print a list of the largest Untouched_Stretches in the summarized Records, each with its file, first and last line number, length in characters, the words that say where it was written (criterion 11) and its Window_Run, ordered by length descending, then path ascending, then offset ascending.
4. THE Reveal_Command SHALL print at most 10 Untouched_Stretches, or the number given by `--top <n>` where `<n>` is a positive integer.
5. THE Reveal_Command SHALL derive the Untouched_Stretches only from the `AI` Spans of the Records, and SHALL report in one line the number of characters in `AI>HUM` Spans that it leaves out of the list, so that no agent text is dropped without being counted.
6. THE Reveal_Command SHALL print a table that groups the `AI` and `AI>HUM` characters by Window_Run, with the Task_Number, the Run_Label, the time the window opened, the number of files and Runs, and the characters of each of the two Origins, ordered by opening time ascending, so that a person can see how much agent text each task or turn left.
7. WHEN a summarized file is a Stale_Record, THE Reveal_Command SHALL mark that file in the output as stale.
8. THE Reveal_Command SHALL give the same output for the same Records, Baseline_File, files and arguments on every run.
9. THE Reveal_Command SHALL print, once, in the summary, the Source_Legend's `[HUM]` item as the notice: `[HUM]` means changed while no agent window was open, and typing, pasting and other tools are not told apart.
10. IF no Record and no Baseline_Entry exists, THEN THE Reveal_Command SHALL print one line that says nothing is recorded and name the setup command, and SHALL exit with status 1.
11. WHEN the Reveal_Command names the window of a Run outside a code, it SHALL say where the text was written in these words: `written in task` followed by the Task_Number, when the window has one, and by the Run_Label, unless the Run_Label is the fallback word `task`, and `written in turn` for a `turn` window, so that text of the window `5.3 Build the view 2026-11-19T10:01:00Z` reads `written in task 5.3 Build the view` (Decision 19).
12. WHEN the Sessions_File holds `noPromptEventSessions` greater than 0, THE Reveal_Command SHALL print in the summary exactly one line, `Sessions with no prompt events: <n> counted. In such a session an edit the agent made between tasks is recorded as [HUM]. The count can miss sessions or count one twice; see Limits.`, with `<n>` replaced by the count and with no other wording, so that the count never reads as exact; WHEN the count is 0 or the Sessions_File is absent, THE Reveal_Command SHALL print no such line; the line is printed whatever path the summary was asked for, because the count belongs to the whole record (Decision 20). IF the Sessions_File cannot be parsed, THE Reveal_Command SHALL print one line that says the count is unreadable and SHALL not change its exit status.

### Requirement 11: `reveal --check`

**User Story:** As a maintainer, I want a command that fails when a record is damaged and reports a record that is behind its file, so that CI can tell a trustworthy record from a damaged one.

#### Acceptance Criteria

1. WHEN `reveal --check` runs, THE Reveal_Command SHALL, for every Tracked_File, read the file, read its Record or Baseline_Entry, parse the Record with `parseRecord`, and compare the Recorded_Text, or the digest of the Baseline_Entry, with the file text.
2. WHEN every Tracked_File has either a Record whose Recorded_Text equals the file text, or a Baseline_Entry whose digest equals the digest of the file text, THE Reveal_Command SHALL print one line that gives the number of files checked and SHALL exit with status 0.
3. IF a Record cannot be parsed or does not satisfy the Engine's own checks, THEN THE Reveal_Command SHALL print one line that names the Record and the reason `tampered_record`, and SHALL exit with status 1.
4. IF a Record exists for a path that is not a Tracked_File, THEN THE Reveal_Command SHALL print one line that names the Record and the reason `orphan_record`, and SHALL exit with status 1.
5. IF a Baseline_Entry exists for a path that is not a Tracked_File, or a path has both a Record and a Baseline_Entry, THEN THE Reveal_Command SHALL print one line that names the path and the reason `orphan_baseline`, and SHALL exit with status 1.
6. IF a Tracked_File has a Record whose Recorded_Text differs from the file text, or a Baseline_Entry whose digest differs from the digest of the file text, THEN THE Reveal_Command SHALL print one line that names the file and the reason `stale`, and SHALL report it without changing the exit status.
7. IF a Tracked_File has neither a Record nor a Baseline_Entry, THEN THE Reveal_Command SHALL print one line that names the file and the reason `no_record`, and SHALL report it without changing the exit status, because a file that appeared after the last event is not yet recorded (Decision 2).
8. WHERE `reveal --check --strict` is run, THE Reveal_Command SHALL exit with status 1 when any `stale` or `no_record` line is printed, in addition to the exit statuses of criteria 3 to 5.
9. THE Reveal_Command SHALL print the reasons in path order, SHALL print every failure and every report and not only the first, and SHALL label each line as `fail` or `report`.
10. THE Reveal_Command SHALL print the exact command that catches the record up (`reveal --record`) on the last line of a run that printed a `stale` or `no_record` line.
11. WHEN `reveal --record` runs, THE Reveal_Command SHALL run the Recorder with the Hook_Event `manual` (Requirement 3, criteria 9 and 10).
12. THE Reveal_Command SHALL perform the check without a network request and without writing any file.

### Requirement 12: The MCP tools

**User Story:** As a developer, I want to ask Kiro which parts of a file I have not touched since it wrote them and get the answer from the record as data, so that the answer does not depend on the model's memory.

3. THE Provenance_Tools SHALL return, for each of `reveal_file`, `provenance_summary`, `untouched_agent_text` and `check_records`, structured content that matches the shape documented in criteria 4 to 7, together with a short text summary of one to five lines, and SHALL declare each shape as the tool's `outputSchema`.
4. WHEN the tool `reveal_file` is called with a path, THE Provenance_Tools SHALL return the structured content `{ file, status, reason, unrecordedCharacters, spans, legend }`, where `status` is `current`, `unchanged_baseline`, `stale` or `unrecorded`, `reason` is `null` or, for `unrecorded`, one of the reasons of Requirement 9, criterion 9, `unrecordedCharacters` is the number of Changed_Characters or `0`, `spans` is an array of Structured_Span in file order that covers every character of the file as of the last recorded event, and `legend` is the four items of the Source_Legend.
5. WHEN the tool `untouched_agent_text` is called with a path and an optional `top`, THE Provenance_Tools SHALL return the structured content `{ path, stretches, countsByOrigin, omittedAiHumCharacters, stale, notice }`, where `stretches` is an array of Structured_Span of origin `AI` in the order of Requirement 10, criterion 3, `countsByOrigin` has the keys `AI`, `AI>HUM`, `HUM` and `PST`, and `notice` is the Source_Legend's `[HUM]` item: `[HUM]` means changed while no agent window was open, and typing, pasting and other tools are not told apart.

WHEN the tool `provenance_summary` is called, THE Provenance_Tools SHALL return the structured content `{ files, total, windows, stretches, omittedAiHumCharacters, noPromptEventSessions, notice }`, where `noPromptEventSessions` is the count of the Sessions_File, or `0` when it is absent or unreadable, and each of `files` and `total` holds the counts and shares by Origin and a `stale` flag, `windows` is an array `{ windowRun, taskNumber, taskTitle, openedAt, files, runs, aiCharacters, aiHumCharacters }`, and `stretches` is an array of Structured_Span with a `file` key. 9. WHEN the tool `setup_provenance` is called, THE Provenance_Tools SHALL perform the installation of Requirement 13, criterion 3, and SHALL return `{ written, replaced, kept }`, the lists of files it wrote, files it replaced and files it kept (Requirement 13, criterion 4).
10. THE Provenance_Tools other than `setup_provenance` SHALL read only the Record_Directory, the Kiro_Ignore_File, the Ignore_File and the files they describe, and SHALL write no file.
11. THE Provenance_Tools SHALL answer from the Records and the Baseline_File and SHALL not call any model.
12. THE Provenance_Tools SHALL take the Workspace_Root from the argument `workspace` when given, else from the current directory of the MCP process, and SHALL walk up from that directory to the nearest directory that holds a Record_Directory. WHEN `setup_provenance` is called without `workspace`, THE Provenance_Tools SHALL use the current directory only if it holds `.git` or `.kiro`, and otherwise SHALL return an error that asks for `workspace`, because where Kiro starts a Power's MCP server is unverified; THE Setup_Skill SHALL always pass `workspace` (Decision 19).
13. IF no Record_Directory is found, THEN THE Provenance_Tools SHALL return an error result that says provenance is not set up in this workspace and names the tool `setup_provenance`.

## Decisions

These record the user's answers to the 17 questions that were open on 2026-11-18. The user accepted every recommendation except where a decision below says it changed. The numbers are the numbers of the questions.

1. **Record directory.** Committed, at `.kiro/provenance/`, with `state.json`, `errors.log` and the lock file ignored by a `.gitignore` inside it. Changed: no Record is written for a file that has not changed since the baseline. One small committed Baseline_File holds the path and SHA-256 digest of each such file. A Record is created at the file's First_Change from the baseline text as `[PST]` with the difference applied. A file that has a Baseline_Entry and no Record, with an unchanged digest, is shown as `[PST]` and is not a fault in `--check`. A conflict in a Record is resolved by deleting the Record and running `reveal --record`; the file then has neither a Record nor a Baseline_Entry, so it is recorded whole with the origin of the event, and that file's history is lost. Requirements 2, 5, 6, 9, 10, 11 and 13 follow.
   - **How the starting text of a Record is obtained (settled by the user on 2026-11-18; Decision 19).** The Baseline_File stores, for each path, the SHA-256 digest and, where git is present, the Blob_Id of the file's exact bytes. At the First_Change the Recorder reads the starting text with `git cat-file blob <id>`, with no limit on commit depth and no walk of history. An ignored cache of starting text, `<Record_Directory>/cache/<SHA-256 digest>`, holds text only for files that git cannot give back: files whose Blob_Id is not in the object store at the baseline (untracked, or modified at the baseline), and every file in a workspace with no git. When neither source has the text, the Recorder records the file's current text as `[PST]` at that event, attributes that change to no one, and writes `baseline_text_unavailable` to the Fault_Log. It never records a whole file as `AI` or `HUM` for this reason, so nothing is over-attributed; the cost is that the one change that arrived with the lost text is not attributed. Measured on 2026-11-18: all 1,064 tracked files' Blob_Ids are in this repository's object store, none is missing, no end-of-line conversion is in effect and the tree is clean, so the cache here would hold 0 files and 0 bytes at a baseline taken on a clean tree; it grows only by the untracked or modified files at the baseline.
   - **What in the design depends on a record existing for every file.** Plainly: anything that reads "the Record of a tracked file" must now also handle "no Record, a Baseline_Entry". That covers: Property 1 (now "Record text equals file text, or Baseline_Entry digest equals file digest"); the check and its reasons (`no_record` used to fail and now reports; `orphan_baseline` is new); `reveal <file>` (an Unchanged_File has no Record to render); the summary totals (an Unchanged_File counts as `PST` from the file text, not from a Record); the MCP tools that return spans (an Unchanged_File returns one `PST` span); rename handling (a rename of an Unchanged_File changes only the Baseline_Entry's path); deletion and exclusion handling (the Baseline_Entry is removed with the file); the cache in `state.json` (a digest compared against the Baseline_Entry as well as against the Record); the size accounting of the Record store; the arbitraries (a Record_Directory may hold a Baseline_File and few Records); the Baseline command (it now writes no Record); the setup tool (it writes no Record); Property 4 (the Baseline_File must also stay byte for byte the same); the README excerpt (it needs a file that has changed); and the recovery from a deleted Record described above. Anything the design wrote that says "every tracked file has a Record" is wrong under this decision.
2. **Stale records.** Kept: named reasons and `reveal --record`. Additions. (1) `reveal <file>` on a stale file says so at the top with the number of characters not yet recorded, and never presents the file as current (Requirement 9, criterion 10). (2) For this repository a git pre-commit hook runs the Recorder catch-up with the Hook_Event `manual`, because Kiro commits in the middle of a window in chat mode; the Setup_Skill only offers that hook elsewhere (Requirement 14, criterion 6; Requirement 13, criterion 7).
