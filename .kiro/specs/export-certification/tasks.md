# Implementation Plan: export-certification

## Overview

The plan builds `packages/export` (`@reveal-codes/export`), a pure TypeScript package with the gate, the statement data and wording, the appendix, the docx builder and the file name, and then wires the Export flow into `apps/web`: the `verifiedAt` Store field, persistence, the working Export dialog, the download, and the print view at `/print`. The Engine and the Verifier are not changed. Order follows the design's task order: probe the `docx` bundling path inside `apps/web` first, then package modules each followed by the property that tests them, then the web changes, then docs.

Task count: **24 tasks**, counted as leaf sub-tasks (numbered `N.M`), checkpoints included (3.4, 5.6, 6.2). The six group headings are not counted. The dependency graph lists the 21 non-checkpoint leaves, as in editor-app. Exactly four properties exist: P1 in 4.4, P2 in 2.3, P3 in 3.2, P4 in 4.2. Each is its own task and none is optional.

Conventions that apply to every task:

- Paths are repository-relative. Source modules stay at 300 lines or fewer and functions at 40 lines or fewer (Req 10.9). No `any`, no default exports outside Next `page`, `layout` and `route` files, no `try/catch` that swallows (tech.md). Errors in `packages/export` are `Result` values; `buildDocx` rejects.
- `packages/export/src` has no `node:` import, no React or DOM, no network call, and reads no clock, random source or environment variable (Req 9.1, 3.11). Imports use `.js` specifiers like the Engine.
- Tests live in `packages/export/test/` and `apps/web/test/`. The `export` Vitest project is pinned to `TZ=America/Los_Angeles` (task 1.1), so every date assertion in the export package is a local date in that zone. Example tests belong to the implementation task that builds the module; they are not separate tasks. No network, no snapshots, no `vi.mock` of the Engine or Verifier (testing.md). Only `fetch` and `LlmProvider` may be faked.
- Property rules (tech.md, testing.md, Req 10.5 to 10.7): each property is one `fc.assert(fc.property(...))` in `<module>.properties.test.ts`, preceded by `// Property N`, inside a `describe` whose title ends in `_Requirements: x.y_`. P1 to P3 use `numRuns` from the `runs()` pattern of `apps/web/test/support/fc.ts` (200 locally, 500 when `CI` or `FC_NUM_RUNS` says so); P4 uses `numRuns: 50` with a comment that packing a docx file is slow. A property must assert a relationship between input and output. On a failing property, record the shrunk counterexample as a named example test and fix the code; never weaken the property.
- Tasks marked "(follows ui.md)" touch `apps/web`: no component, icon or CSS library, one global stylesheet plus one CSS module per component, palette `#FFFFFF`, `#111111`, `#B0B0B0`, `#ECECEC` with accent `#1F3A8A` only for focus and links, no shadows, radius, gradients or transitions, 13px UI sans, text labels only, no exclamation marks, no toasts. The existing static scans in `apps/web/test/static` enforce this.
- Standing Known-limitations rule: a finding that affects only malformed input or a rare style is recorded as one `L<n>` line in `requirements.md` and `design.md` (next free number is L5), with no spec change and no stop.
- Any task that adds or changes a hook, steering file, agent or MCP tool also needs a row in `docs/KIRO_USAGE.md` (structure.md). Task 1.3 adds the hook; its row, and the rows for this spec and the steering edits, are written in task 6.1.
- Task completion notes record anything Kiro got wrong and the fix, for the BUILD_LOG entry in task 6.1.
- `.env.example` is not touched by any task (Req 11.5).
