# Implementation Plan: editor-app

## Overview

The plan builds `apps/web`, the Reveal Codes editor, in TypeScript on Next.js (App Router, webpack), TipTap and ProseMirror. The Engine and Verifier source is not changed; the only edit to a package outside `apps/web` is the `exports` metadata of `packages/verifier/package.json` (Req 1.8). Order: setup and an API smoke test, pure editor modules (offsets, step mapping), the Store with history and persistence, the editor and page shell, the Pane, the server and Verify flow, the Issues list and demo path, then Tier 2 (the assistant), then docs.

Task count: **37 tasks**, counted as leaf sub-tasks (numbered `N.M`), checkpoints included (3.5, 5.5, 7.5, 9.4). The nine group headings are not counted. The dependency graph lists the 33 non-checkpoint leaves, as in citation-verifier. Tier 2 tasks are 8.1, 8.2, 8.3 and 9.1, plus the Tier 2 clauses named in 9.2 and 9.3.

Conventions that apply to every task:

- Paths are repository-relative. Source modules stay at 300 lines or fewer and functions at 40 lines or fewer. No `any`, no default exports outside Next `page`, `layout` and `route` files, no `try/catch` that swallows (tech.md, Req 2.4 to 2.8).
- Tests live in `apps/web/test/`. Example tests belong to the implementation task that builds the module; they are not separate tasks. No network, no snapshots, no `vi.mock` of the Engine or Verifier (Req 25.7). Only `fetch` and, in Tier 2, the stream function are faked. The server `sleep` in route tests is a real abortable timer, never an instant one (design, Server).
- Exactly five properties (Req 25.1). Each is one `fc.assert(fc.property(...))` in a file named `<module>.properties.test.ts`, preceded by `// Property N`, inside a `describe` whose title ends in `_Requirements: x.y_`. `numRuns` comes from `test/support/fc.ts` `runs()`: `FC_NUM_RUNS` if set, else 500 when `CI` is set, else 200. Arbitraries are shared: Engine ones from `packages/engine/src/testing/arbitraries.ts`, app-specific ones in `apps/web/test/arbitraries.ts`. Properties are core and none is optional. A property that only checks that a function does not throw is not a property. On a failing property, record the shrunk counterexample as a named example test and fix the code; never weaken the property (testing.md).
- Rendering tests start with `// @vitest-environment jsdom` and use `@testing-library/react`; Properties 1 and 2 use `EditorState` and `Transaction` with no `EditorView` and no DOM (Req 25.5).
- ui.md binds every task that touches `apps/web`: no component, icon or CSS library, one global stylesheet plus one CSS module per component, the UI palette (`#FFFFFF`, `#111111`, `#B0B0B0`, `#ECECEC`, accent `#1F3A8A` only for focus and links), no shadows, radius, gradients or transitions, 13px UI sans, text labels only, no exclamation marks, no toasts. The Pane keeps its own CGA palette and is exempt. The static scans of task 1.3 enforce this.
- Standing Known-limitations rule: a finding that affects only malformed input or a rare citation or editing style is recorded as one `L<n>` line in the Known limitations section of `requirements.md` and `design.md` (next free number is L21), with no spec change and no stop.
- Task completion notes record anything Kiro got wrong and the fix, for the BUILD_LOG entry in task 9.3.
- Any task that adds or changes a hook, steering file, agent or MCP tool also adds its row to `docs/KIRO_USAGE.md` (structure.md).
- Tier 2 tasks are marked "(Tier 2)". Removing them and the Tier 2 clauses listed in the design's "Tier 2 cut list" changes no other task.
- Property map: P1 in 2.2, P2 in 2.4, P3 in 3.3, P4 in 5.2, P5 in 6.4.
