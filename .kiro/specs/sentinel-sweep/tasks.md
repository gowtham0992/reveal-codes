# Implementation Plan: sentinel-sweep

## Overview

The plan builds the sweep CLI in `crew/sentinel` (`@reveal-codes/sentinel`) in four groups. Group 1 sets up the package and builds the read side: `readDocx`, `splitExport`, the error kinds, `recordedDocument`, and the test support every later test uses. Group 2 builds the re-check side: `reverify`, `buildDeps`, the Findings and `analyseFile`, plus Property 1. Group 3 builds the report side and the runner: renderers, argument parsing, file access, the sweep, `run`, `cli`, Property 2, the save hook, and the static boundary tests. Group 4 writes the documentation and steering edits and ends with the single final checkpoint. The Engine, Verifier, MCP server and `apps/web` are not changed. `packages/export` changes only by the two added exports of task 1.1.

Task count: **25 tasks**, counted as leaf sub-tasks (numbered `N.M`), the final checkpoint (4.6) included. The four group headings are not counted. The dependency graph lists the 24 non-checkpoint leaves. Exactly two properties exist: Property 1 in 2.6 and Property 2 in 3.2. Each is its own task and neither is optional.

Conventions that apply to every task:

- Paths are repository-relative. Source modules stay at 300 lines or fewer and functions at 40 lines or fewer (Req 1.11). No `any`, named exports only, no default exports, no classes (Req 1.10). Errors are `Result` values; the only `try/catch` blocks convert a thrown error into a value, a Finding, or an exit code and message, and none is empty (Req 1.12). Imports inside `crew/sentinel/src` use `.js` specifiers like the Engine.
- Tests live in `crew/sentinel/test/`. Example tests belong to the implementation task that builds the module; they are not separate tasks. No network, no snapshots, no `vi.mock` of the Engine or Verifier. Only `fetch` is faked, through `recordedFetch`. No test imports `docx`; `.docx` inputs come from `buildDocx` and are edited with `fflate` (Req 12.1, 12.2).
- Property rules (`tech.md`, Req 12.14 to 12.16): each property is one `fc.assert(fc.property(...))` (an `asyncProperty` for Property 1) in `<module>.properties.test.ts`, preceded by `// Property N`, inside a `describe` whose title ends in `_Requirements: x.y_`. Property 1 uses `numRuns: docxRuns(process.env)` (50 when `FC_NUM_RUNS` is unset, else `min(FC_NUM_RUNS, 100)`, with a comment that packing a `.docx` is slow). Property 2 uses `runs(process.env)`. A property must assert a relationship between input and output. On a failing property, record the shrunk counterexample as a named example test and fix the code; never weaken the property.
- Every task that edits `crew/sentinel/src/index.ts` is 1.1 (empties it) or 3.5 (writes the public surface), so no two tasks in one wave touch it.
- Steering, hook and docs rows land in the group named by the user's plan: the hook file is task 3.6, and its `docs/KIRO_USAGE.md` row is written with the other two rows in task 4.2, as the export-certification spec did.
- `BUILD_LOG.md` gets exactly one new entry for this spec (Req 13.3). Task 1.1 creates it with the criterion-17 outcome; task 4.3 completes the same entry.
- Commits: the only commit this plan asks for is the `pnpm-lock.yaml` commit in 1.1. Code commits belong to the task hook. Commits of spec files use the prefix `spec(sentinel-sweep):`.
- `.env.example` already lists the four env names and is not edited by any task (Req 13.7). No `app.json` is created (Req 1.14).
- Task completion notes record anything Kiro got wrong and the fix, for the BUILD_LOG entry in task 4.3.
